## Goal

Make Muse Wonder the driver of the existing asset design tool, generating through its own subscription image API rather than the tool's key-based generator. For each asset a pack needs, Muse writes the brief, generates the lottery through the Muse image tool, judges every output as good or bad with a reason, feeds the winners back as references, and narrows round by round until the graphic is the one the game should ship. Every asset run is captured as an asset session, and every generated image is a Muse tool call, so the run is accounted in the Muse session and cost centre as well as in the asset tool's own records. The first fill is the crumbling pack in `.worktrees/mech-5-crumbling-tile`, whose four tile assets are labelled placeholders today. The human reviews the finished assets, not the intermediate lottery.

## Success Criteria

- Muse runs the whole loop for one asset without a human in the middle: brief, generate through the Muse image tool, judge, refine, stop, publish.
- Each asset's run exists as one asset session whose turns contain the imported Muse images in order, whose judgements record Claude's verdicts, and whose turns name the Muse session that generated them; nothing is generated outside a session.
- Spend is capped per asset at a hard $2 (target $1): at $0.01 per generated image that is at most 200 images, and the loop is expected to stop far earlier; the cap is enforced by counting imported outputs in the asset session, not from the model's memory.
- Each of the four crumbling assets (`crumbling.png`, `crumbling-minor.png`, `crumbling-major.png`, `void.png`) ends as a generated 512x512 graphic in `tools/static/packs/crumbling/assets/`, distinguishable from its neighbours at the in-game 64px tile size, with the placeholder files gone.
- The game still passes its suites, and a screenshot of `mech-5-crumbling-tile-room` shows the real art in play for human review.

## Approach

The split of labour follows where each capability already lives. Generation belongs to Muse: the `image_generation` tool in the Muse session produces one image per call through the subscription, accepts local reference images for directed revisions, and is the call the cost centre sees. The asset tool remains the system of record: its backend is already the sole writer of `assets/manifest.yml`, `assets/sessions.yml`, and `assets/judgements.yml`, and it already provides sessions, judgements with a preferred flag, reference carry-over that sorts preferred outputs first, and publish. What the tool cannot do today is hear about an image it did not generate itself: turns record outputs only inside `_run_turn`, which shells out to `scripts/gen-image`, and the upload endpoint stores a file without attaching it to any session. The integration is therefore one new import path through the same records, not a second pipeline.

Under that integration, one asset run is one asset session created through the existing API before any image exists. Each lottery round is one turn: Muse generates the round's images with the image tool (ten calls for a full lottery, fewer as the search narrows), the images are uploaded and imported into that turn with the prompt that produced them, the Muse session id recorded on the turn's existing `provider_session` field, and the turn's cost written as its image count at the tool's $0.01 estimate. Muse then views the imported outputs in place, writes a good/bad verdict with the visual reason for each through the judgements API, marks the best preferred, and composes the next turn's prompt from those verdicts, passing preferred outputs to the image tool as reference images for the next round. Because the winner-selection state therefore lives in the asset session (verdicts, preferred flags, references) rather than in the conversation, any later Muse session can resume an asset exactly where the last one stopped.

Style consistency across the four assets is handled by construction rather than by hope: the intact tile is generated first, its winner becomes a standing reference image for the minor tile, the minor winner joins the references for major, and the void is briefed against all three so the hole reads as the same floor, fallen.

## Steps

1. **Session import in the asset tool** (`tools/asset_store.py`, `tools/server.py`, tests in `tools/test_asset_tool.py`). Add `POST /api/sessions/<id>/turns/import` accepting a prompt, references, uploaded file names previously sent to `POST /api/uploads`, a Muse session id, and a source marker. It appends one completed turn whose outputs are those uploads under lottery-style keys, resizes each to the asset's declared width and height with ffmpeg while preserving the raw file as `-orig` (the same treatment `scripts/gen-image` already applies, since the image tool's size is a ratio carrier rather than exact pixels), stores the Muse session id on the turn's `provider_session`, and writes `cost_total` from the image count. Add an `author` field to judgements so a verdict records whether Claude or the human wrote it, and a read-only outputs-and-spend summary on the session view, which is the number the budget cap is enforced against. The key-based generation path (`scripts/gen-image`, `_run_turn`) stays untouched for human use.
2. **Driver bookkeeping CLI** (`tools/asset_driver.py` with tests). The loop's judgement happens in the Muse session, so the CLI owns only the record-keeping Muse should not do by hand: `brief` composes a turn prompt from a pack manifest's `shows` text, the candidate mechanic's stage definitions, and the tool's checklist constraints; `import-turn` uploads generated files and posts the import call; `status` prints a session's imported outputs, verdict coverage, and spend against the cap. It talks to a running asset server over HTTP only and never writes the YAML records or pack files directly. A `--dry-run` briefing mode spends nothing.
3. **The driving loop, run by Muse.** Per asset: register the asset in the tool if it is not already there (`POST /api/assets`, 512x512, since sessions cannot be created for an unknown asset), create the session, brief, generate ten images through the image tool with the game's published floor and wall art among the reference images, import them as turn one, view every output, and record verdicts. Before any output may be called good it must pass the tool's checklist as the driver applies it: 512x512 after normalisation, fills the frame, square corners, shows what the manifest says it shows, and — the decisive check — still reads correctly downscaled to 64px beside its stage neighbours, because a crack pattern that only exists at 512px does not exist in the game. Later turns shrink (ten, then at most four, then at most four) and pass the preferred winners as reference images. The loop stops on a checklist pass or at the budget cap, keeping the best-so-far and reporting the failed check rather than spending past the cap.
4. **Fill the crumbling pack** (in the worktree `.worktrees/mech-5-crumbling-tile`). Run the loop for the four assets in order (intact, minor, major, void) against the running main-checkout asset server. Publish each winner through the tool's existing publish endpoint, then place the published file at `tools/static/packs/crumbling/assets/<file>` under the exact name the manifest already declares, replacing the generated placeholders. Update no manifest entries: the names, kinds, and `shows` text are already correct, which is the point of having written them first.
5. **In-game verification.** Restage the level sprites in the worktree, capture `mech-5-crumbling-tile-room` at load and after a crossing so intact, minor, and major tiles are all visible in one frame, and run the pack and crumbling suites plus the full suite once. Attach the screenshot and the four asset session ids to the feature as a review-fixes task on the crumbling board item, and leave the feature in `in_review` for the human verdict on the art itself.

## Validation Plan

- `python -m unittest tools.test_asset_tool -v` after the tool changes, covering import (turn created, outputs keyed and resized, `provider_session` and `cost_total` recorded), judgement authorship, and the session summary, and proving existing human generation records are undisturbed.
- `python tools/asset_driver.py brief` in dry-run mode for one crumbling asset, showing the composed prompt with zero spend and no session created.
- One real end-to-end loop on the intact tile only, then a pause for review: the asset session shows every generated image imported in order with a Claude verdict on each, the Muse session shows the matching image calls, and recorded spend is at or under the cap.
- `python -m unittest tools.test_pack_folders tools.test_mech_5_crumbling_tile -v` in the worktree after the fill, then the full worktree suite once, expecting only the two pre-existing `test_pm_review_ui` failures.
- A viewed screenshot of the room with all three crumble stages visible, checked at full size and read at tile size for stage distinguishability.
