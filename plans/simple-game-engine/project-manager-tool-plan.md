## Goal

Build a `project-manager-tool`: a local web UI, served by the existing `tools/server.py`, that manages the work for the simple game engine described in [init-plan.md](/home/andrew/Sites/meta-global-ai-hackathon-jolly-challenge/plans/simple-game-engine/init-plan.md). Work is two-level: a **Feature** is a player-facing capability specified with [template.md](/home/andrew/Sites/meta-global-ai-hackathon-jolly-challenge/plans/simple-game-engine/template.md) (e.g. keys-and-locks), and each feature breaks down into one or more **Tasks**, the small implementation units that actually get picked up, moved across the board, and commented on. The tool shows features and their tasks as a list and as a kanban board, supports full create/edit/archive plus drag-to-change-status, and lets both a human and an agent leave structured comments, including screenshot evidence. It is seeded with the initial game-engine features, each already broken into tasks, so the board is useful on first open.

Implementation is driven by Muse Code from its interactive prompt — there is no new driver script and no automation harness. A human opens Muse Code, points it at a feature or task, and Muse Code does the work in an **isolated git worktree**. There are **no GitHub PRs**: the feature itself, rolled up in the web UI, is the review unit (our "PR"). The human reviews the rolled-up feature in the UI — its tasks, comments, screenshots, linked play sessions, and a playable Test Level from the worktree — approves or requests changes there, and **Muse Code performs the merge** to `main`, promptly, so later features build on it. The human never runs git merges.

Because the base game engine (per the new "Base Game Engine" section of [init-plan.md](/home/andrew/Sites/meta-global-ai-hackathon-jolly-challenge/plans/simple-game-engine/init-plan.md)) must be deterministic with JSONL session logs, replay, and forking from a replay point, human review is not screenshots alone: play sessions in Test Levels or real levels are recorded as labelled sessions (who created them — human or agent), findable and replayable in the game UI, and linkable from board comments, so a reviewer can pinpoint exactly where something went wrong instead of guessing from a still image.

Decisions from the project owner's reviews (2026-10-29): (1) structured backend store is source of truth, YAML preferred, SQLite acceptable if it removes concurrency problems; markdown is a generated export/view; (2) full CRUD + drag kanban + comments; (3) scope is the tool plus seeding initial game features/tasks — building the game is later work through those tasks; (4) model is Feature → Task; (5) statuses are `proposed | approved | in_progress | in_review | completed | blocked | abandoned`; (6) `priority` only, no due date/estimate/assignee; (7) archive replaces hard delete; (8) standalone page at `/static/project-manager.html`; (9) Muse Code guided by **both** a project skill **and** an instruction file, prompted interactively — no new script; (10) worktrees live inside the repo under `.worktrees/` (gitignored); (11) review is in the web UI, not GitHub: tasks roll up into the feature for human approval, the agent attaches screenshots as proof, the human can playtest the branch in a Test Level / Mechanics Playground, and a feature is `completed` when the human marks it so after playtesting; (12) merges (including conflict resolution) are done by the agent after human approval; (13) humans and the AI may both create features, but a feature must be human-`approved` before implementation starts; (14) review fixes are an intermediate step, not edits to the original task's history; (15) "approve for merge" is a distinct recorded action, not the same moment as `completed`, merges happen promptly per feature, "Request changes" is an explicit UI action requiring a comment, template declares whether a feature needs a mechanics playground, playtest/test-level launching lives in a game-engine menu (not the manager), the human gates are convention for a single human rather than hard enforcement, and screenshot evidence is kept; (16) the base engine is deterministic with JSONL session logs, replay, and fork-from-a-point in a replay, with sessions labelled by creator and findable/playable in the game UI.

## Success Criteria

- Opening the tool shows every seeded feature with its tasks nested under it in list view and, after toggling, the same tasks grouped in kanban columns by `status`, filterable by feature, with no data difference between views.
- A human can create/edit a feature, create/edit/archive a task under it, drag a task card to another column, and add a comment — all surviving a server restart. The AI can also create a feature, which then sits at `proposed` until a human approves it.
- A human can type one prompt in interactive Muse Code (e.g. "work on `keys-and-locks`") and Muse Code, following only the shipped skill + instruction file: finds the feature and its next task, claims it (`in_progress` + agent comment), creates/reuses the feature's isolated worktree and branch, implements and verifies the task, commits it, and updates the task (`in_review` + comment with what changed, how it was verified, and screenshot evidence where the change is visual/playable) — with no new script run and no hand-editing of the store file.
- A feature at `in_review` presents one review page in the UI: all its tasks rolled up with statuses and evidence comments, screenshot gallery, its Test Level, and a playtest entry (worktree path, start command, and URL) so the human can play the branch themselves.
- The human uses an explicit **Approve for merge** action in the UI after playtesting; Muse Code then merges the feature branch into `main` promptly, resolves any conflicts, re-runs tests on `main`, records the merge, sets the feature `completed`, and cleans up the worktree — the human performs no merge.
- A play session in the game (Test Level or real level) is recorded as a JSONL session labelled with its creator (`human` or `agent`); a reviewer can find it in the game UI's session list, replay it move by move to pinpoint where it went wrong, and fork a new playable session from any point in that replay. Agent and human playtests for a feature are linked from its board comments as session evidence, alongside screenshots.
- A feature's progress (e.g. 2/5 tasks done) is derived from its tasks, never typed in by hand.
- Every feature exports to markdown under `plans/simple-game-engine/features/` whose spec sections match `template.md`, with tasks rendered as a section.
- Existing tools are unregressed: the asset-design UI at `/`, the level preview at `/static/level-preview.html`, and the existing unittest suites still pass.

## Approach

Reuse the repo's established local-tool pattern: a backend-owned store with atomic writes, a JSON API on the stdlib HTTP server, and a single-file vanilla-JS page. This mirrors the asset tool — [asset_store.py](/home/andrew/Sites/meta-global-ai-hackathon-jolly-challenge/tools/asset_store.py) owns `assets/*.yml` behind `StoreError`-validated functions with header-preserving, `os.replace`-atomic `_save_yaml` writes, [server.py](/home/andrew/Sites/meta-global-ai-hackathon-jolly-challenge/tools/server.py) exposes them under `/api/*` behind `STATE_LOCK`, and [level-preview.html](/home/andrew/Sites/meta-global-ai-hackathon-jolly-challenge/tools/static/level-preview.html) proves a static page is served via `/static/*`. No new pip dependencies: `pyyaml==6.0.3` is already in [requirements.txt](/home/andrew/Sites/meta-global-ai-hackathon-jolly-challenge/requirements.txt); the permitted fallback, SQLite via stdlib `sqlite3`, adds none. Single-user local tool on `127.0.0.1:8321`, same trust model as existing tools. Screenshot capture reuses the existing headless-Chrome approach in [tools/capture_level.sh](/home/andrew/Sites/meta-global-ai-hackathon-jolly-challenge/tools/capture_level.sh) / `capture_level.py`, extended from the preview page to the game page.

### The two-level model

| Level | What it is | Spec source | Worked on by | Delivered as |
|---|---|---|---|---|
| Feature | Player-facing capability; the "what and why" | `template.md` sections | Human or AI creates it; human approves it; Muse Code implements it | One worktree/branch, one in-UI feature review, one agent-performed merge |
| Task | One implementation unit, small enough to finish and verify in one sitting | Title + description + acceptance note | Muse Code (or a human) in the feature's worktree | One commit on the feature branch |

Rules: every task belongs to exactly one feature (no orphans in v1; a chore means a small feature); features depend on features (`requires`), tasks may depend on tasks, and starting before `requires` are `completed` warns but never blocks; `unblocks` is derived as the reverse of `requires`, never stored; task status is set directly (drag/form/agent via API); feature status follows the review lifecycle below. Progress (`n/m`) is always derived.

### Feature lifecycle (review and merge, without GitHub PRs)

```text
Feature:  proposed ──(human approves)──▶ approved ──(agent claims first task)──▶ in_progress
          in_progress ──(agent: tasks done, evidence posted)──▶ in_review
          in_review ──(human: explicit Request changes + comment)──▶ in_progress   [via a review-fixes task]
          in_review ──(human: explicit Approve for merge)──▶ in_review, review.decision = approved_for_merge
          approved_for_merge ──(agent merges promptly, verifies on main)──▶ completed, merged recorded, worktree removed
Task:     proposed → approved → in_progress → in_review ──(feature merge)──▶ completed   (blocked / abandoned are side states)
```

- **Approve for merge** is a distinct recorded action (owner's NQ15 "sure"): the human's UI action sets `review.decision = approved_for_merge` with timestamp while the feature stays visibly `in_review` (badged "approved — awaiting merge"); `completed` is set only by the agent after the merge verifies on `main`. The board therefore never shows `completed` for code not yet on `main`.
- While a feature is `in_review`, its tasks are `in_review` too — implemented and evidenced, but not `completed` until the merge lands. The progress bar therefore reads honestly during review.
- **Request changes** is likewise explicit (NQ17): a UI button that requires a comment, records `review.decision = changes_requested`, and moves the feature back toward `in_progress`; the agent finds pending change requests by API alone (`review.decision`), without the human having to re-prompt with the details.
- Merges are the agent's job, promptly per feature (NQ16): on approval (or the human's "merge `keys-and-locks`" prompt), Muse Code merges the feature branch into `main` from the main checkout — merge commit, preserving the per-task commits — resolves conflicts itself (reporting any conflict it cannot resolve safely rather than guessing), runs the test suites and a game smoke check on merged `main`, and only then sets feature and tasks `completed`, records `merged`, posts closing comments, exports markdown, and removes the worktree and branch. Merging sooner, not batching, is deliberate: later features branch from a richer `main`.

### How Muse Code works a task

The human drives everything from the interactive Muse Code prompt; Muse Code uses only its normal tools (file reads/edits, shell, git) plus the project-manager API. The contract ships **both** as an instruction file and as a project skill that loads it (owner's NQ8 answer):

1. **Point and pick up.** Human prompt, e.g. "work on feature `keys-and-locks`". Muse Code (via the skill) reads the instruction file, fetches the feature and tasks from the API (`GET /api/pm/features/<id>`; if the server is down the file's start/check procedure applies, and if it still cannot reach it, it reports instead of improvising), checks the feature is human-`approved` (AI-created features sit at `proposed` until then — it must not start, only offer to flesh out the spec) and that `requires` features are `completed`, then selects the first open task in `order` unless one was named.
2. **Claim.** Via the API: task → `in_progress`, plus an `agent` comment stating what it will do and how it will verify it. Already `in_progress` means stop and tell the human — two sessions never work the same task.
3. **Isolate.** One git worktree and branch per feature, created on first pickup and reused for all its tasks: branch `feat/<feature-id>` from current committed `main`, worktree at `.worktrees/<feature-id>` inside the repo (gitignored, owner's NQ9 answer). Code work happens only inside the worktree. The store file (`pm.yml`) and exported `features/*.md` are never committed on a feature branch — board state lives on `main` and is written only through the API, so the feature diff is code/tests/levels only.
4. **Implement and verify one task at a time**, including its Test Level/playground changes where the task calls for them (below): read the feature spec and the task's `acceptance`, make the smallest change, run the verification (unit tests; for playable changes, run the game from the worktree on a spare port and play the flow), and fix until green. Existing repo tests must still pass.
5. **Evidence and commit.** For any visual or playable change, capture screenshots of the worktree build (extending `tools/capture_level.py`/`capture_level.sh` to the game page and the feature's Test Level) and, once the engine supports it, record an agent-labelled play session of the Test Level; attach both to the task's completion comment (screenshot attachments, session id/path). One commit per task on the feature branch, message carrying the task id. Then via the API: task → `in_review` with an `agent` comment — what changed, commit hash, exact test evidence, attached proof. Blocked instead: task → `blocked`, comment what is needed, human told in chat, worktree left in place.
6. **Roll up for review.** When all of a feature's tasks are `in_review`, the agent sets the feature `in_review` and posts a feature-level `agent` comment: task roll-up, screenshot gallery, linked sessions (level, creator, result), and how to playtest — worktree path, exact server start command from the worktree on its spare port, and the game URL, from whose own menu the human starts the Test Level or opens a linked session replay. The human reviews entirely in the web UI — no GitHub involved.
7. **Changes requested → review-fixes step.** The human clicks **Request changes** (comment required, recorded as `review.decision = changes_requested`). The agent, finding that decision via the API, creates a distinct **`review-fixes` task** (numbered per round: `review-fixes-1`, `review-fixes-2`, …) holding the requested changes as its description/acceptance, works it through steps 2–5 in the same worktree, and returns the feature to `in_review`. Original tasks' history stays untouched (owner's NQ14 answer: review-fixes as an intermediate step).
8. **Approve, merge, close out.** Human playtests (own session, or replaying the agent's linked sessions in the game UI) and clicks **Approve for merge**. Prompted to merge, the agent promptly performs the merge workflow under "Feature lifecycle," sets feature and tasks `completed`, removes `.worktrees/<feature-id>`, and deletes the merged branch. If the merge conflicts or tests fail on `main`, it stops, reports, and leaves the branch/worktree intact.

Parallel features: one Muse Code session per feature worktree, never two sessions in one worktree or branch. Board writes stay serialized through the single server on `main`.

### Test Levels / Mechanics Playground

A feature that changes gameplay is verified in a **Test Level / mechanics playground**: a small, purpose-built level whose only job is to exercise that mechanic in isolation (a debug room), in the established level format of [levels/chip1.json](/home/andrew/Sites/meta-global-ai-hackathon-jolly-challenge/levels/chip1.json) (rows + legend). This is not strict per feature (owner's NQ18 answer): [template.md](/home/andrew/Sites/meta-global-ai-hackathon-jolly-challenge/plans/simple-game-engine/template.md) declares for each feature whether it needs a playground, reuses an existing one, or needs none — and what to check there — and the human reviews that declaration with the spec.

- The **game engine itself** owns launching them (NQ19): the game UI has a menu listing Test Levels/playgrounds with a start action, next to the session browser below. The project manager never starts levels; its review page only identifies the feature's `test_level` and links to the worktree build's game URL.
- The feature record stores `test_level` (level name or null). Where a new or extended playground is needed, building it is an explicit task in that feature; a combined "Mechanics Playground" level with one room per mechanic may grow incrementally from these rooms rather than being seeded as a separate strict structure.
- Screenshots and recorded sessions offered as review evidence are captured from the feature's Test Level in the worktree build wherever the change is playable.

### Session logs, replay, and forks (base engine, review-critical)

From the "Base Game Engine" requirements the owner added to [init-plan.md](/home/andrew/Sites/meta-global-ai-hackathon-jolly-challenge/plans/simple-game-engine/init-plan.md): the engine must be deterministic, keep session logs of play as JSONL files, replay a session, and fork a new session from a point in a replay. In this plan that is seeded work for the game (a feature below), with a defined contract the project manager relies on for review evidence:

- **Deterministic core, with a real counting clock.** Game state advances only through a pure step function: given the initial level plus the ordered, timestamped input log, the same run always produces the same states. The timer is a real counting clock, not one tick per move (owner's NQ22 answer): it counts down in real time while playing, and every input is recorded with its elapsed time (`t_ms` since session start), so the timer value at any step is a function of the log, never of unrecorded wall-clock reads. Rendering is a view of state, not a driver of it. This is what makes replay exact rather than approximate, and the seeded engine features (`game-shell`, movement) must be built to it, not retrofitted.
- **Session file (JSONL).** **Every** play is recorded (NQ23) — real levels and Test Levels, finished, lost, or quitted. One file per session under `sessions/` (gitignored, like `screenshots/`): a header line `{type: "session", id, created_at, created_by: "human"|"agent", label, level, level_source (file + hash), feature, task, branch, commit}`, one line per step `{type: "step", n, t_ms, input}`, a closing line `{type: "end", result: won|lost|quit, steps, orbs_left, time_left}`, and, appended afterwards, annotation lines `{type: "annotation", at, by, labels: [...], note}`. Annotations are how a session gains **notes and labels after the fact** (e.g. `failed`, `bug` — NQ23): they live in the same file, replay ignores them, and the Sessions list can filter by them. The **creator label** (`created_by`, plus optional free-text `label`) is the "who created that session" data the owner asked for; `feature`/`task`/`commit` trace it to the exact build.
- **Find and replay in the game UI.** The game has a Sessions menu (beside the Test Levels menu): list/filter sessions by level, creator, feature, date, result, and annotation labels; add/edit notes and labels on a session there. Open one to replay it with play/pause, step forward/back, and a position scrubber; at any step the UI shows step number, position, inventory, orbs left, timer, and the input that caused it, so a reviewer can pinpoint where things went wrong. Sessions open by **deep link** (NQ24): `?replay=<session-id>&step=<n>` lands on that exact session at that exact step, so a board comment can point at the precise failing move. Replaying against a different engine/level version than the header records must warn, not silently diverge.
- **Fork from a replay point.** Pausing a replay at step *n* and choosing "Fork from here" starts a new playable session seeded from the replayed state at that step. Its header carries `forked_from: <session id>`, `fork_step: n`, and **`forked_by`** (NQ25), and keeps the original session's `created_by`, so a fork stays grouped with the session it came from while still recording who forked it; the Sessions list shows these fork chains. This is the debugging move the owner described: reproduce a failure once, then try a different action at the exact step it went wrong.
- **Only the game loop needs to be deterministic** (NQ26). Procedurally generated levels are produced outside the game loop (there is no in-game generator UI/agent loop to replay); a generated level is just a level file by the time it is played. The session header's level identity + hash therefore suffices — the generator itself never needs to be deterministic or replayable from a seed.
- **Link into review.** When an agent or human playtests a feature (worktree Test Level or a real level), the session id/path is attached to the task/feature completion comment, just like a screenshot attachment. The feature review page lists linked sessions with level, creator, and result, and links to the worktree game's Sessions menu (or a `?replay=<session>` deep link if the game supports it — NQ24), so the reviewer opens the exact session instead of re-performing it. Because a worktree — and any session files recorded inside it — is deleted at close-out, the agent copies linked session files into the main checkout's `sessions/features/<feature-id>/` before worktree removal (same preservation rule as screenshots), and the stored link points at that surviving copy.

Key decisions:

1. **Store: one YAML file, backend-owned, SQLite as escape hatch.** New `tools/pm_store.py` (modeled on `asset_store.py`) owns `plans/simple-game-engine/pm.yml`; the server loads it into `STATE` and is its only writer; atomic, header-preserving saves. If testing still shows lost updates, switch `pm_store.py` internals to SQLite (`pm.db`, stdlib) behind the same signatures — API/UI unchanged; the switch has a written trigger, not a silent rewrite.
2. **Feature schema maps 1:1 onto `template.md`, plus delivery fields.** `id`, `title`, `summary`, `status`, `priority` (`low|medium|high|urgent`), `requires`, the ten template text sections, `branch`, `worktree` (path), `test_level`, `review` (`{decision: pending|changes_requested|approved_for_merge, by, at}` set only by the human's UI actions), `merged` (`{commit, at}` set by the agent after merging), `sessions` (linked play-session refs: id, path, level, created_by, result — see the replay section), `archived`, `created`/`updated`, `comments`.
3. **Task schema is deliberately small.** `id` (unique within feature; global ref `<feature>/<task>`), `feature_id`, `title`, `description`, `acceptance`, `status`, `priority`, `requires`, `order`, `commit`, `archived`, `created`/`updated`, `comments`. Plus `kind` (`feature` work vs. `review-fixes`, default work) so review rounds are distinguishable in the roll-up.
4. **Statuses (owner's set):** `proposed → approved → in_progress → in_review → completed`, plus `blocked`/`abandoned`. Kanban columns are these seven. Who may set what matters more than the list: humans set feature `approved` (gate to start) and, via **Approve for merge**, the merge gate; the agent sets everything else, including `completed` after a verified merge. For a single human this is convention, not enforcement (NQ20): the API records who did what (comment/review authorship and timestamps make it visible), and the instruction file states the agent must never approve its own feature — no harder gate is built.
5. **Comments carry screenshot and session evidence.** Comment: `id`, `author` (`human`|`agent`), `created`, `body` (markdown), `attachments` (evidence image paths), `session_refs` (linked play sessions). Status/priority/archive changes render inline in the same chronological thread. Humans create/edit/delete their own comments; `agent` comments are read-only in the UI. The server serves attachment files through a guarded route (e.g. `GET /api/pm/evidence/<path>`, resolved under the evidence root only), and the UI renders thumbnails in the comment and the feature review gallery, and session refs as labelled rows (level, creator, result) linking toward the game's replay. Screenshot evidence lives under `screenshots/features/<feature-id>/` and is **kept** after close-out (NQ21), not pruned or committed.
6. **Agent entry point: instruction file + project skill, no script.** Canonical text: `plans/simple-game-engine/agent-workflow.md` (the 8-step workflow, API/`curl` examples, server start/check, worktree commands, commit format, screenshot procedure, PR-equivalent roll-up comment template, review-fixes loop, merge and close-out checklists, and hard rules: no store/export commits on feature branches, never start an unapproved feature, never work an already-`in_progress` task, never mark a feature `completed`, stop-and-report on unmet `requires` or unsafe merge conflicts — **plus the exact merge procedure**, since merges are the agent's job). A project skill for Muse Code, created in whatever project-skill location Step 4 verifies this build actually loads (the repo has none today), triggers on work-on/review/merge prompts and loads that one file. The human's example prompts ("work on…", "feature `x` is ready for review", "merge approved features", "close out…") live in both the file and the README.
7. **Markdown export: one-way, feature-level, on demand.** Export button (`POST /api/pm/export`) renders `plans/simple-game-engine/features/<id>.md` from the `template.md` layout — frontmatter (`title`, `summary`, `status`, `priority`, `requires`, derived `unblocks`), ten spec sections, a `## Tasks` section (status, acceptance, commit, and evidence filenames), and feature `## Comments`. Generated header, nothing read back.
8. **Frontend: one standalone page, three views over one dataset.** `tools/static/project-manager.html`, vanilla JS + `fetch`. (a) List: features as expandable rows (status, priority, derived progress, requires, branch) with nested tasks. (b) Board: task cards across the seven status columns, feature filter on top, drag-and-drop writing `status`+`order`. (c) Feature review: the per-feature roll-up page from workflow step 6 — tasks and evidence comments, screenshot gallery, linked sessions (level, creator, result, replay link), Test Level identification and game-URL link (starting the level happens in the game's own menu), worktree path/start command, and the human's explicit review actions (**Request changes**, comment required; **Approve for merge**). Detail panels for editing feature/task with comment threads (edit/delete only on own human comments), Archive buttons, show-archived toggle. Loud error banner on API failure, as in `level-preview.html`.

Seed features and starter tasks (from `init-plan.md` + `docs/game-lore-and-mechanics.md`), seeded idempotently through the API/store. A feature gets a Test Level/playground task only where its template declaration calls for one; the agent may also propose new features later (at `proposed`, awaiting human approval). ## Steps

1. **Store — `tools/pm_store.py` (new), `plans/simple-game-engine/pm.yml` (new, on first run).** Mirror `asset_store.py` (header-preserving atomic YAML, `StoreError`), normalizers for feature/task/comment/attachment, CRUD + archive, status setters enforcing the human gates for agents (decision 4), comment add/edit/delete, `move_task`, and helpers `feature_progress`, `derived_unblocks`, `review_rollup`. ## Risks / Open Questions

Risks:

- **R1 — Concurrent writes.** Only the server writes the store; worktree sessions use its API, so the old lost-update hazard is designed away. Two sessions claiming at once is handled by the claim check. SQLite fallback behind `pm_store.py` stands if Step 1 testing still loses updates.
- **R2 — Board files vs. feature branches.** `pm.yml`, `features/*.md`, and `screenshots/` change on `main` while branches fork older code; they are never committed on feature branches, so merges cannot conflict on them. The cost: a worktree's local board files are stale — the agent must read board state from the API, never its worktree files.
- **R3 — Merge conflicts are now agent work.** Features branched from an ageing `main` (or parallel features touching the same game files, likely for `game-shell` vs. `hud`) can conflict at merge time. The workflow requires the agent to stop and report unsafe conflicts; sequencing features by `requires` and merging promptly after approval keeps this small. The current dirty `main` working tree (R4) must be committed or set aside before the first worktree branches from it — the dry run will surface this.
- **R4 — Dirty `main`.** Substantial uncommitted work exists on `main` today. Worktrees branch from committed `main` only; this plan neither commits nor discards that work, and Step 7 names its base commit explicitly.
- **R5 — Playtest servers die with sessions.** A server started from a worktree by an agent session may not outlive it, so the review page must always carry the start command, not just a live URL (decision: the stored URL is informational; the command is canonical).
- **R6 — Determinism must precede mechanics.** Replay is exact only if no mechanic smuggles in wall-clock time, rendering callbacks, or unseeded randomness. The seeded order enforces this (`game-shell` builds the deterministic core before movement/timer features), and every later feature's acceptance should include a replay check: record a session, replay it, same end state. A feature that breaks determinism breaks every session recorded before it — hence the version-mismatch warning rather than silent divergence.
- **R7 — Evidence lives in worktrees until preserved.** Screenshots and session JSONL produced in a worktree vanish when it is removed. The workflow already copies linked sessions to `sessions/features/<feature-id>/` on `main` before cleanup; the Step 7 dry run must verify a linked session still opens after its worktree is gone.
