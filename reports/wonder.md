# Jolly's Challenge — Challenges, Technical Uncertainty, and Workflows

This report collects the challenges that the project encountered, the technical uncertainties that it set out to reduce, and the workflows that were built in response, so that a reader who has not followed the day-to-day development can understand what was attempted, what was learned, and what remains open. The project is a tile-based puzzle game in the tradition of Chip's Challenge, in which the player guides Jolly through enclosed levels, collects orbs in order to open a gate, and reaches a portal before a timer expires, and it was built during a ten-day hackathon under a set of deliberate constraints that shaped nearly every technical decision. Because those constraints and the central research question explain why so much of the effort went into tooling rather than directly into levels, the report begins with them before turning to the individual systems.

## The central uncertainty and the constraints that framed it

The question recorded in `docs/technical-uncertainty.md` is whether an agent can design levels that are fun and creative, rather than merely correct, because prior game projects by the same author had repeatedly reached a playable state and then stalled on level design and pacing, which depend on creative judgement and therefore required extensive manual playtesting and adjustment. The hackathon was scoped as an experiment against that background, in the sense that the game was intentionally kept small enough that the boundary of what an AI model can deliver in level design might become observable, rather than being obscured by the sheer size of the engine or the asset set. That framing matters for reading the rest of the report, because much of the work described below is measurement infrastructure, and it exists so that claims about level quality can be checked against recorded play rather than asserted from a passing test run.

The constraints recorded in `docs/technical-limitations.md` were to keep Meta Model API spend within $150, to use only assets generated by Muse Image 1.0 or newer, and to use only Muse Spark 1.3 or newer through Muse Code, even though a subscription and access to Muse Wonder were also available, because the aim was to replicate the limitations that other hackathon participants were under. Those constraints were treated as a design input rather than as background bookkeeping, which is why cost tracking and key management were built before the game itself, and they also explain why several later findings take the form of a cost observation, such as the relative effectiveness of different models at different effort levels for user-interface work. Where the constraints were later relaxed in practice, most notably in the use of Wonder at low and medium effort for interface fixes after Spark at extra-high effort had struggled, the relaxation is recorded as a finding rather than concealed, because it bears directly on how similar projects should budget model use.

The choice of game followed the same pattern of narrowing scope until the experiment became tractable. An initial interest in Wolfenstein 3D was set aside because the game was judged too complex for a ten-day budget, and an initial plan for a Sokoban clone was set aside for a different reason, which was that Sokoban concentrates its difficulty in demanding logical puzzles that the author found frustrating rather than enjoyable. Chip's Challenge was selected instead, following the research summarised in `docs/game-testing-research.md` and `docs/game-env.md`, because it retains the small tile grid and the restartable room structure of Sokoban while distributing its perceived complexity across novel mechanics and a time limit, so that the player is rewarded for progress without being required to sustain the same depth of logical search on every room. The takeaways recorded from playing both reference games, namely that the game should not mentally exhaust the player, should not make replay after a dead end feel tedious, should continue to feel fresh as mechanics accumulate, and should tell a story toward an end goal, subsequently served as the criteria against which mechanics and teaching rooms were judged.

## Safeguarding spend before building anything else

Two community tools were created before the hackathon proper began, Meta Cost Center and Meta Keyguard, because the $150 limit could only be enforced if every model call and every image call were captured in one place and if the API keys that incurred those calls could be revoked automatically when the limit was reached. Cost Center records usage by project and model and can raise an alert that is wired to Keyguard, so that when the configured monthly threshold for the project is reached, the named keys are destroyed and further spend stops, rather than merely being reported after the fact. Keyguard in turn issues time-limited keys, stores them outside the repository, and supplies them to local tooling through a retrieval command, so that scripts never need to embed a long-lived secret and so that revocation has a concrete target to act on.

The integration work that followed from those tools is representative of the project's general approach, in which a workflow is only considered finished once its side effects are visible in the system of record. Muse by default does not attribute spend consistently across subscription and pay-as-you-go use, so a Muse hook was installed through Cost Center in order to collect that information, and the image generation script described in the next section was required to report each successful call exactly once, with the model, the number of images returned, the project, and the key label when the key had come from Keyguard. The care taken over the key label illustrates why the detail matters, because the revoke alert matches on that label, which means that a generation performed with an unlabelled key would be counted in cost terms but would not be stoppable by the kill switch, and the tooling was therefore written so that the normal path always preserves the label and so that a failure to record warns without discarding an image that has already been paid for.

## Generating game art through a script the agent can drive

Muse Code did not have direct access to Muse Image 1.0, so the project built `scripts/gen-image` as the single route through which both the human and the agent generate images, using the OpenAI SDK because the Meta Model API is OpenAI-compatible and does not provide its own SDK. The script loads its key through `meta-keyguard get`, accepts a prompt directly or from a file, accepts dimensions and aspect ratio, accepts up to ten reference images for edit-style generation, and can request between one and ten output images in a single call, and it reports the call to Cost Center after success so that image spend participates in the same budget as model spend. Keeping generation behind one script meant that later tools, including the asset design tool and the asset driver, could invoke the same tested path as a subprocess rather than each reimplementing authentication, sizing, and accounting.

Two findings from the early use of that script shaped its final form. The first was that the image API treats the requested size as an aspect-ratio carrier rather than as exact pixels, so that a request for 512 by 512 could return a 1600 by 1600 file while the script's own summary still reported 512 by 512, a discrepancy that was noticed by an external model review rather than by the script's author and that would have propagated silently into every downstream sprite if it had not been corrected. The script now resizes the returned image locally with ffmpeg to exactly the requested width and height while preserving the raw generator output alongside it with an `-orig` suffix, so that the file the game consumes has deterministic dimensions and the original evidence remains available for inspection. The second finding was that a command-line generation script, however correct, does not by itself support iteration, because prompts, outputs, and human judgements about those outputs still have to be tracked somewhere, and that gap motivated the asset design tool described next.

## The asset design tool and the discovery that iteration was not happening

The iterative asset design tool, planned in `plans/asset-design-tool/iterative-asset-design-tool.md` and implemented as a local Python service in `tools/server.py` with storage in `tools/asset_store.py`, exists so that tile art can be iterated from a browser interface rather than by hand-editing YAML. The backend is the sole writer of `assets/manifest.yml` and `assets/judgements.yml`, using atomic writes through a temporary file and rename, and each asset holds a chain of versioned prompts in which a new version can name a parent version and thereby inherit the parent prompt text, the parent output image, and the parent judgement for review. A run invokes `scripts/gen-image` once as a subprocess under a single-run lock, records the output under `assets/outputs/` with a timestamped key, surfaces the estimated cost and any recording warning, and leaves the human to record a free-text judgement keyed by output name, so that the reason a prompt was changed is preserved beside the image it produced.

The most instructive failure in this part of the project was the discovery, documented in `plans/asset-design-tool/investigate-gen-flow.md`, that three successive versions of the default floor tile had not improved at all, in the specific sense that cracks persisted and rounded corners persisted despite version names that suggested otherwise. Investigation against the stored records showed three compounding causes. Every version had sent a byte-identical prompt to the model, as confirmed by a shared hash prefix, because the complaints about cracks and corners had been written into the version description and into human judgements, neither of which the model ever sees. In addition, on a new version's first run the parent image was not sent at all, so that those runs were fresh text-only generations rather than edits of the previous image. Each so-called iteration was therefore an independent draw from the same prompt, and the outputs differed only by sampling variation, which explains why none of the three requirements that mattered for tiling, namely absence of cracks, square corners, and edge-to-edge fill, had ever been present in a prompt the model received.

The response to that failure proceeded in two stages, and the distinction between the stages is worth preserving because the first stage repaired the mechanics of iteration while the second stage repaired its shape. The first stage made the prompt the single source of truth that is shown verbatim before a run, added a guard that blocks a new version's first text-only run when its prompt is identical to its parent's, and introduced a draft builder that composes a new prompt from the parent prompt together with constraint sentences derived from failed checklist items, covering frame coverage, square corners, cracks, weathering, and seamless tiling in a three-by-three arrangement. The lottery extension in `plans/asset-design-tool/lottery-image-design.md` then allowed one run to produce between one and ten images for roughly one cent per image, with up to ten reference images selected individually from prior runs, per-image notes and optional judgement carry-over, and a batch judging view from which a winner could be marked preferred and carried into the next version, because at that price generating several candidates and selecting among them is more effective than attempting to perfect a single prompt in advance.

The second stage, described in `plans/asset-design-tool/multi-turn-improved-ui.md`, recognised that even a correct version chain forces every prompt to carry the entire description of the desired tile, whereas the image model improves more naturally through short corrections applied against visible context. A spike established that the OpenAI-compatible images API exposes no provider session or continuation parameter, so the tool emulates a session by keeping an ordered thread of turns in a third backend-owned file, `assets/sessions.yml`, and by automatically carrying prior session outputs as reference images, preferred images first and newest first up to the ten-image cap, unless the user ticks specific images or explicitly requests a fresh text-only turn. Each turn records the exact prompt and reference list that were sent, together with a provider-session field that remains null under emulation so that a future provider session identifier could be adopted without changing the interface or the publish path, and publishing remains the only route by which iteration state enters the official manifest, appending a new version to an existing asset name or creating the asset when the name is new, reusing the output file so that judgements carry over, and never overwriting a published image. The context tray, which holds uploaded reference images beside published outputs and provides a copy-name action for pasting a filename into the prompt box, reflects the same lesson in interface form, which is that iteration improves when the material being iterated on is visible and nameable at the point of writing the next instruction.

Several broader observations about Muse Image 1.0 emerged from sustained use of the tool and are recorded in `docs/minimal-graphical-assets.md`. The model was found to be unusually literal, so that direct prompting by a human was frequently less effective than having Spark or Wonder at low effort compose the prompt, whereas with careful prompting the results were judged comparable to or better than a competing image model. Stylistic consistency across independently generated tiles remained difficult throughout, and an experiment in which a full Chip's Challenge level screenshot together with Jolly was supplied as a reference in the Muse Playground produced a more consistent composite level than tile-by-tile generation had achieved, although it struggled with wall structure, which suggests that a reference-screenshot workflow in which individual graphics are extracted from a consistent whole may be worth revisiting when budget allows. The tool itself was also the site of a model-selection finding, because Spark at extra-high effort struggled with a series of user-interface fixes, documented across the asset tool plans, whereas Wonder at low and medium effort completed the same class of work more cheaply and more reliably, which led to the working hypothesis that Wonder at lower efforts can fill the role that might otherwise require a larger model tier.

## Grounding generated art in the shipped sprites and judging it at game scale

A later workflow, the AI asset driver in `plans/ai-asset-driver/PLAN.md` with its companion `plans/ai-asset-driver/GROUNDING.md`, extended the asset tool so that Muse could run the iteration loop without a human in the middle of each round. Under that workflow Muse writes the brief from a pack manifest, generates a lottery of candidates through the Muse image tool, views every output, records a good or bad verdict with a visual reason through the judgements interface, marks a preferred winner, and composes the next turn from those verdicts with winners passed forward as reference images, while the asset tool remains the system of record through a session import path that attaches externally generated images to a turn, normalises their size, records the Muse session that produced them, and counts imported outputs against a hard per-asset spend cap of two dollars. The bookkeeping command-line interface in `tools/asset_driver.py` deliberately owns only the record-keeping around that loop, such as composing a brief, importing a turn, and reporting spend against the cap, because the judgement itself belongs in the session that can see the images, and live YAML run reports under `plans/ai-asset-driver/reports/` capture each round's references and verdicts at the moment they happen rather than reconstructing them afterwards.

The grounding document exists because the first driver run for the crumbling tile family produced art that was plausible stone in isolation and yet wrong for the game in two specific ways that its own judging had passed. The surface did not match the shipped floor sprite in `tools/static/level-sprites/floor_default.png`, because generation had been guided by a text description of light grey stone rather than by the sprite file itself, and the crack marks were realistic hairlines at 512 pixels that became effectively invisible when the tile was rendered at the 64-pixel size the game actually uses, at which scale one displayed pixel corresponds to eight source pixels. The two rules that follow from that failure now govern the driver. Every generation for a floor-family asset must pass the real floor and wall sprites as reference files, and staged damage should ideally be produced by editing the floor sprite itself so that the undamaged stage is the game's floor by construction, with stage-to-stage winner references added in addition to the ground sprites rather than instead of them. Every candidate must be judged downscaled to 64 pixels beside the real floor and its neighbouring stages, with crack strokes on the order of eight to twelve pixels wide at source size and near-black against the light stone, because a mark that vanishes at camera scale does not exist in the game regardless of how it appears at full resolution, and the final check is an in-room screenshot at playing scale rather than inspection of the source files.

## Seeing a level before there was a game

The level preview tool, planned in `plans/level-preview-tool/plan.md` and served from the same `tools/server.py` process, renders level layouts from `levels/*.json` in the browser with PixiJS using keyed sprites derived from `assets/published` by `tools/prep_level_sprites.sh`, so that a level could be evaluated visually before the playable game shell existed. The first level, `chip1`, is a seventeen-by-sixteen transcription of the original Chip's Challenge layout in `docs/chips-first-level.png`, produced with Muse Spark vision and expressed as rows together with a legend that maps each character to a label, a sprite, and where relevant a key or lock colour, because that representation is small enough for both a human and an agent to read, edit, and diff. Key and lock colour variants were initially derived by hue rotation as placeholders, with real variants deferred to the asset tool, which kept the preview unblocked on art completion while preserving a clear record of which sprites were provisional.

The preview became a closed visual loop through headless capture, because `tools/capture_level.sh` and `tools/capture_level.py` render the page in headless Chrome through Playwright and write timestamped screenshots into `screenshots/`, with an optional side-by-side comparison against a reference image, so that Muse Code could view its own rendering, compare it against the source level, and correct transcription or sprite errors without waiting for a human to describe them. That same capture path was later generalised to the game page and to per-feature evidence, which is why screenshots under `screenshots/features/<feature-id>/` function as review material rather than as incidental debugging output. The lesson that carries beyond this tool is that an agent working on visual material needs a deterministic way to produce an image of its current state on demand, at a stable size and from a stable route, because without that capability visual defects are reported in prose long after the change that caused them, whereas with it they can be inspected in the same session that introduced them.

## A deterministic engine with recorded play from the first build

The game engine was specified from the outset, in the `game-shell` feature, around a pure and deterministic step function, in which a given initial level together with an ordered and timestamped input log always produces the same sequence of states, and in which the timer at any step is a function of recorded elapsed time carried on each input as `t_ms` rather than of unrecorded wall-clock reads at render time. Rendering is defined as a view of state and never as a driver of it, so that the PixiJS board, the heads-up display, and the replay player all read the same state that the step function produced. That discipline was adopted before movement, keys, or orbs existed, because retrofitting determinism after mechanics have each introduced their own timing assumptions is substantially harder than holding every mechanic to the rule that state advances only through the step function.

Session recording follows from determinism and was present from the first playable build rather than added as diagnostics afterwards. Every play writes a JSON Lines file under `sessions/` through `tools/game_sessions.py`, consisting of a header that records the session identifier, creation time, creator, level, level source hash, and where available the feature, task, branch, and commit, followed by one line per step carrying its index, timestamp, and input, followed by a closing line with the result and final counters, after which append-only annotation lines may be added without rewriting history. The game posts the accumulating file content as play proceeds, so that a session exists from the first move and no play is unrecorded even if the browser is closed mid-attempt. Because a session plus its level fully determines the resulting states, replay is not a video but a recomputation, which is what makes the later quality gate possible, since a recorded session that does not replay to its recorded end state is evidence of nondeterminism rather than a difference of interpretation.

The replay interface built on top of those records, in `tools/static/game-replay.js` together with the session handling in `game-session.js` and `game.js`, allows a reviewer to open a session from a deep link of the form that names a session and a time in seconds, to scrub and step through events on a unified timeline, to inspect state at the selected step, to annotate a step, and to fork play from that step with the recorded clock continued rather than restarted, while version warnings surface any mismatch among level hash, engine version, and commit so that stale proof is visible rather than silently divergent. The interface required an unusual amount of iteration, as the commit history for `session-logs-replay` shows through successive attempts involving an overlay component library and a parameter-editing control panel, neither of which produced a usable operator tool, before a redesign informed by interface-design and usability skills settled on an unobstructed game viewport, one playback timeline and control bar, and a compact step inspector beside the board. That history is itself a finding, because it demonstrates that a model can implement correct replay mechanics considerably earlier than it can arrange those mechanics into an interface that a reviewer can operate without instruction.

On top of the shell, the base game was delivered as a sequence of individually reviewed features, namely player movement and collision, the level timer with loss at zero and restart, coloured keys and locks with an eight-slot inventory, orb collection with a gate that opens only at zero orbs remaining, warp-based level progression with an inter-level summary and wipe transition, and a heads-up display showing time, orbs, level, and inventory. Each feature was required to preserve determinism, so that even apparently presentational concerns, such as freezing the timer and state on death or victory, or covering the incoming level from the first paint so that no white flash precedes the wipe, were handled as state and transition rules that replay could reproduce. The heads-up display also exposed a limitation in generated graphical user-interface art, because elements that must be sliced precisely into digits, labels, and backplates proved difficult to generate directly, and the shipped sprites under `tools/static/gui-sprites/` were completed by generating partial assets in the Muse Playground and finishing them in Illustrator and Photoshop, a reminder that tile art and interface art place different demands on a generation workflow even at the same nominal resolution.

## The project manager as the review unit for agent work

Because the base game and the later mechanics were to be built by an agent under human review, the project built its own project manager rather than relying on external pull requests, and the design of that tool is inseparable from the development workflow that the rest of the report assumes. A feature is a player-facing capability specified through the template in `plans/simple-game-engine/template.md`, which requires a goal, a user story, a high-level use case written for a player rather than an engineer, concrete player-facing behaviour, edge cases, interface feedback, assets and level data, acceptance criteria, and a testing declaration, and a feature breaks down into tasks, which are the small units that are claimed, implemented, and committed. The store is `plans/simple-game-engine/pm.yml`, owned by `tools/server.py` through `tools/pm_store.py` and written only through the HTTP interface, with generated Markdown exports under `plans/simple-game-engine/features/` and screenshot evidence under `screenshots/features/`, because allowing either the human or the agent to hand-edit the store would have made board state diverge from the history that the interface displays.

The canonical contract for agent work is `plans/simple-game-engine/agent-workflow.md`, which the project skill in `.claude/skills/work-on-feature/` loads on triggers such as a request to work on a named feature, and which defines an eight-step progression from pickup through claim, worktree isolation, implementation and verification, evidence and commit, roll-up for review, review fixes, and finally human approval followed by an agent-performed merge. One feature corresponds to one branch and one Git worktree under `.worktrees/<feature-id>`, one task corresponds to one commit whose message names both identifiers, and the feature as rolled up on its board page, with its tasks, comments, screenshots, and linked play sessions, serves as the review unit in place of a pull request. The human approves a feature before work begins, playtests the worktree build on a spare port while the board server remains on its own port, and either requests changes, which the agent picks up from the recorded decision without requiring the details to be repeated in chat, or approves the feature for merge, after which the agent merges, verifies the test suites and a game smoke check on the main branch, preserves linked session files that would otherwise be lost with the worktree, records the merge through the interface, and only then allows the feature to become completed. The hard rules that support that flow, including that the agent never starts an unapproved feature, never works a task another session has claimed, never commits board state on a feature branch, and never marks its own feature completed or approved, exist because each of the corresponding failures would otherwise be easy to commit accidentally and difficult to detect from the board alone.

Sustained use of the tool produced findings that qualify its success in useful ways. The frontend, which is a React application using HeroUI version 3 and Tailwind version 4 built with Vite from `tools/web/` into `tools/static/app/`, became necessary after the initial interface proved difficult to keep usable as the board grew, and graphical interface work in general remained the area in which the models struggled most, a pattern that recurred in the replay interface and that improved only after interface-design and usability skills from skills.sh were introduced into the workflow. At the same time, the act of moving between the interactive Muse Code session and the board interface made communication through board comments less natural than communication in chat, whereas a hosted system with comment hooks might have closed that loop more directly, and the anticipated parallel execution of tasks by subagents did not materialise, because the codebase and the review model both favoured one feature at a time with human review at each step. The retrospective judgement recorded in `docs/pm-and-simple-game-engine.md` is therefore that the tool was useful but could have been simpler for the single-threaded workflow that actually occurred, and that feature development typically cost between five and ten dollars per feature, a figure that is difficult to evaluate in isolation but that raises the question of how code organisation affects the cost of agent implementation, which is the question the engine refactor then took up.

A practical consequence of the worktree-per-feature model at the scale the project eventually reached, with dozens of mechanic worktrees present at once, was an accumulation of running tool servers on forgotten ports, so that finding the server for a particular worktree or shutting one down became a recurring annoyance recorded in `docs/game-engine-refactor.md`. The response was a worktree manager in `tools/worktree_mgr.py` together with a worktrees page in the tools application, which discovers registered Git worktrees, reports which of them have a listening server and on which port, and can start a server for a registered worktree on the next available port or stop one it manages, while deliberately never removing worktrees, branches, or files, because lifecycle decisions about feature branches belong to the merge checklist rather than to a convenience page. The manager is a small component, but it illustrates a recurring pattern in the project, in which a workflow that is sound for one feature at a time requires dedicated tooling once the same workflow is instantiated seventy times in parallel.

## Refactoring a working monolith into a kernel and packs

By the time the base game was complete, its logic lived in large monolithic files in which movement, collision, pickup, warp, gate, timer, rendering, heads-up display, and input responsibilities were intermixed, and keys and locks in particular had been coupled into the core after the fact, so that adding each further novel mechanic would have required the agent to read and modify an increasing amount of unrelated code. The refactor was therefore approached as an audit before it was approached as code, through the prompt preserved in `plans/game-engine-refactor/PLAN.md`, which required a map of the current architecture, an inventory of every place the core hardcoded a specific tile or mechanic, a proposal for the boundary between a minimal engine kernel and additive packs in the style of an internal mod system, a pressure test of that proposal against hypothetical mechanics, and a phased migration in which every phase left the game fully playable. The pressure test is worth noting in its own right, because requiring the design to accommodate water that is lethal without a carried item, a button linked to a trap on another tile, a monster with its own movement rules, and ice or force floors that move the player after a step, all without touching engine code and without implementing any of them, forced the proposal to provide general primitives, including linked tiles, a generic inventory, per-tile metadata, and a fixed step pipeline, rather than accommodations shaped around the mechanics already present.

The resulting architecture separates a deterministic kernel in `tools/static/engine/kernel.js` and a registry in `tools/static/engine/registry.js`, which together own the layered grid of terrain, objects, and actors, the generic state containers for inventory, counters, flags, links, and per-cell metadata, and the fixed step pipeline, while knowing no specific tile, item, or mechanic, since every rule arrives through registry definitions and pack hooks identified by namespaced identifiers. Timer, orbs, and gate were placed in a core pack built through the same registration system that other packs use, rather than retained as kernel privileges, so that the game's defining mechanics exercise the same extension path that a novel mechanic must use, and keys and locks were extracted as the first example pack in order to prove that path against a mechanic that was known to be coupled. A compatibility facade in `tools/static/game-core.js` assembles the registry, kernel, and packs and preserves the long-standing public interface, including a derived projection of the layered state into the legacy grid, player position, orbs remaining, and gate-open values that tests and the game page already consumed, so that the migration could proceed behind a stable surface and be verified by identical readouts rather than by inspection.

The migration was guarded by two mechanisms that together made a behaviour-preserving claim checkable. A regression corpus captured readouts and state digests for recorded play before the kernel was extracted, so that each subsequent phase could be required to reproduce those values exactly, and a kernel purity gate in `tools/check_kernel_purity.sh` counted mechanic-specific literals, such as orb, warp, key-colour, and gate terms, in kernel-bound files against a recorded baseline, with the expectation that the count would shrink to zero as packs were extracted, which it did for the kernel scope once the core pack and the keys-and-locks pack had been separated. Proof packs for water with flippers, buttons and traps, ice and force floors, and a patrolling monster were built during the refactor to exercise the pressure-test cases in running form, after which the button, ice, and monster packs were discarded while the water pack was retained, because their purpose had been to validate the architecture rather than to ship as game content. Packs themselves became folders rather than single scripts, each carrying a `main.js`, a `manifest.json` that mirrors the asset list in the corresponding candidate mechanic file, and an `assets/` directory for bundled files, with the registry deriving load locations from declarations so that no loader maintains a hardcoded list, a structure documented in `tools/static/packs/README.md` that later allowed the asset driver to fill a pack's declared files without modifying its manifest.

Two renderer concerns were resolved in the same period and are recorded here because they determine how every later level appears. A camera in `tools/static/engine/camera.js` provides pure viewport mathematics for levels larger than the screen, supporting levels up to sixty-four by sixty-four tiles while clamping smaller levels to the origin so that they render as before, and a fixed world scale in `tools/static/engine/world-scale.js` pins the on-screen tile size to sixty-four pixels for every level, so that small levels letterbox, large levels present a scrolling window, and the camera only translates the board without ever rescaling it, which keeps tiles square and sprite aspect intact regardless of a level's own declared tile value. One review correction in this area is instructive, because framing more tiles than fully fit the available area at the fixed scale placed the player in the cropped portion of the view at a level's edges, so the visible view is now derived from the tiles that fully fit, capped by both the level size and the camera maximum, in order to guarantee that Jolly remains in frame. An attempt during the refactor period to implement four proposal packs concurrently produced four packs that did not work correctly, which reinforced the earlier project-manager finding that feature development in this codebase needs to proceed one session and one feature at a time, even when the architecture has been designed to make packs independent in principle.

## Planning one hundred mechanics without designing levels one at a time

Level and mechanics planning began with the intention of designing each level individually and adding mechanics as the design required them, but that approach was judged too labour-intensive to sustain, so the project instead asked Muse to propose one hundred candidate mechanics, which the human then reviewed with annotations and enriched with synergies, demonstrations, and teaching moments before deciding to carry the full set forward as features, as recorded in `docs/level-and-mechanics-planning.md`. The candidates are stored as structured YAML under `plans/level-design/candidate-mechanics/`, grouped into families covering movement tiles, keys and locks, orbs, switches and doors, enemies and bots, terrain and hazards, gear and items, blocks, vision and information, and time gates and exits, and the schema described in that directory's README is itself a substantive design artefact, because it determines what an agent must understand before a mechanic can be approved. Each entry must define every shared term its rules use, referencing the mechanic that introduced a behaviour where the behaviour is borrowed, must state its rules as an explicit list, must declare the assets its pack will bundle grouped by kind, must name synergies in which two mechanics combine to produce a decision neither provides alone as distinct from demonstrations in which two mechanics are merely contrasted for teaching, and must include a teaching moment together with named test cases.

The teaching moment and test case requirements deserve particular attention, because they encode the project's answer to the fun-versus-frustration findings from the reference games. A teaching moment describes the first encounter with a mechanic as a single scenario that states how the room is arranged, what a player who has not yet understood the mechanic is likely to do, how that action fails, and how the player recovers, on the reasoning that the recovery is what converts the failure into the lesson, provided that the failure arrives soon after introduction, is attributable to the one rule being taught, costs only a restart of a small room, and is immediately followed by success once the rule is understood. Test cases must correspondingly include the solution path, one adversarial case involving backtracking, hesitation, or the naive action the teaching moment warns about, a boundary case at exact counts or timings, and restart plus replay, with the standing rule that a reachable state with no legal move and no loss or reset is a failure of the mechanic rather than an acceptable outcome, and with cases that depend on unbuilt mechanics marked as blocked rather than silently omitted. Test rooms were consequently conceived in kinds, covering sanity checks of a single mechanic, synergy rooms that test cross-feature interaction, contrast rooms, and teaching rooms, with sanity rooms built first, because a mechanic that cannot be shown correct in isolation cannot be evaluated fairly inside a composed level.

From those candidates the project generated a mechanic-sanity-checks programme of seventy-three features comprising two hundred and nineteen tasks, in which each feature follows the same pattern of building a teaching test level, implementing the mechanic as a pack, and performing a sanity check by playing the room, as exemplified by the exported specifications under `plans/simple-game-engine/features/`. In parallel, a tentative level roadmap under `plans/level-design/roadmap/` explored how finished mechanics might be sequenced into levels, beginning with a human-authored first level as a template, continuing with an AI-authored keys-and-doors level whose name required human correction before acceptance, and arriving at a third candidate in which colour matching taught within the initial view is combined with a scrolling path, off-screen orbs, and a lock placed beyond the first screen before the gate. That roadmap is the point at which the project comes closest to its central uncertainty, because sequencing mechanics so that novelty sustains interest without exhausting the player is precisely the creative judgement whose automation the hackathon set out to probe, and the evidence so far shows AI-authored candidates being accepted with human correction and combination rather than accepted or rejected wholesale.

## Proving that a mechanic works rather than that its code passes

The quality framework in `plans/qa-framework/PLAN.md` was written because the base game demonstrated a specific evidential gap that unit tests could not close on their own. Sessions had been recorded throughout, but their headers frequently carried null values for feature, task, branch, and commit, most ended in a quit rather than a win, and nothing linked a given session to the acceptance rule it was supposed to prove, while the workflow at the time described recording as something to do once the engine supported it and no step verified that a recorded session replayed to the same end state, even though mechanic specifications already promised a replay digest match. Human review consequently caught defects that green suites had missed, including a game menu that opened the full reference level instead of the intended small test room and timer and sprite faults that only appeared in play, because the existing tests drove the engine core under Node with scripted inputs and never exercised the recorded-session-to-replay path that a reviewer actually uses. The framework's premise is that the machinery for stronger evidence already existed in the deterministic core, the JSON Lines sessions, the replay player with time-based deep links and forking, and headless screenshot capture, so that the missing element was criteria and enforcement rather than new tooling.

The framework organises evidence into four tiers with one hard gate between implementation and review. Unit tests prove rule logic in isolation, level checks prove that a teaching room loads through the game menu path rather than merely from its file, that its mechanic tiles are placed, that a scripted winning log reaches a win, and that an empty log does not, session replay proves that recorded play actually occurred and is deterministic at specification strength, and human playback allows the reviewer to scrub and fork the agent's success session from the feature page without rerunning anything. The gate is implemented by `tools/verify_mechanic_qa.py`, which loads a feature's linked sessions, replays each through the engine core, compares the final state digest against the recorded closing line, asserts readout values at annotated steps against magnitudes stated in the specification, checks header linkage and creator, and requires at least one agent session ending in a win, one labelled naive-failure session that performs the teaching moment's obvious but wrong first action, and coverage of playable edge cases, while also confirming that the teaching room is not winnable with no input. A feature for a mechanic sanity check may therefore enter review only when it carries a completed verification task whose comment pastes the verifier report together with a table that maps every player-facing rule to the tier, test name, or session segment that covers it and an interaction audit that marks how the new mechanic meets each existing family it can encounter, because uncovered rules and unconsidered interactions are predictable defect classes when seventy-three mechanics must eventually share rooms.

The plan is also explicit about what it borrowed and what it rejected after reading two game quality skills in full, and that discrimination is part of the workflow finding. Ideas that were adopted include asserting design-intent magnitudes rather than weak positivity checks, treating a no-input win as a failure, auditing entity interactions for asymmetries that a human should review even when they are not automatic failures, and reporting expected against actual values with new failures separated from known baseline gaps in the completed base game. Ideas that were rejected include adopting a browser-automation stack, screenshot pixel differencing, clock mocking, frame-rate and load-time tests, and touch and accessibility variants, on the grounds that a turn-based keyboard grid without randomness, audio, or a frame loop already obtains exact state equality through digests and already advances time only through recorded timestamps, so that importing a second stack to reprove determinism would add instability rather than evidence. The completed base-game features were to be retro-checked under the same verifier with their known gaps reported as baseline, and the framework was to be piloted end to end on a single mechanic before being applied to the remainder, because a gate that has never been satisfied by a real feature cannot distinguish between a high standard and an impossible one.

## The crumbling tile as a worked example of review correcting a mechanic

The crumbling tile feature, candidate mechanic five from terrain and hazards, provides the clearest single illustration of how specification, adversarial play, and human review interact in this project, because its shipped behaviour differs in instructive ways from its first implementation. The mechanic is defined by the observation that the tile is safe while the player stands on it and falls one move after the player leaves it, becoming void for the remainder of the attempt and thereby burning the retreat path so that visit order matters, with restarts and checkpoints restoring it, and its teaching room places an orb beyond a crumbling crossing together with something worth returning for, so that a player who crosses, collects, and turns back discovers the rule through the missing tile. The terms on which the correctness of that description depends, including floor as always-safe walkable ground, wall as never enterable, void as a hole whose entry is falling and therefore loss of the attempt, and orb as a collectible counted by the gate rather than carried in inventory, are defined inside the candidate entry itself, because a later dispute about whether stepping into void should block movement or end the attempt could only be settled by appeal to that definition.

The commit sequence for the feature shows seven rounds of review fixes after the initial implementation, test level, and replay-digest sanity check, and the content of those rounds shows review operating on rules rather than on presentation. Successive corrections established that the fall occurs on the leaving step without creating a bridge soft-lock, that void is a hazard whose entry loses the attempt, that crumble stages become visible in minor and major forms, that leaving rather than stepping on advances those stages so that stepping onto a major tile is safe while leaving it drops it to void behind the player, and that death and victory freeze both timer and state, after which the pack was restructured into the folder form with bundled assets and filled first with generated art and then with a grounded rerun under the rules described earlier. The adversarial case carried in the specification, in which the player crosses two tiles and presses back twice so that the vacated tiles must be void, backward presses must be blocked, and the forward exit must remain reachable with no floating middle tile, is representative of why the solution path alone is insufficient evidence, because each of the corrected behaviours is invisible on a single successful crossing and apparent only when the player hesitates, backtracks, or re-enters a damaged tile. The feature as exported therefore records both an earlier step-on reading of stage timing and the later leaving-based reading that superseded it, which preserves the reasoning trail that a future mechanic with staged damage will need to consult.

## Cross-cutting findings on models, skills, and agent workflows

Several findings recur across otherwise unrelated parts of the project and are collected here because together they describe how agent-assisted development behaved in practice on this codebase. The first concerns parallelism, because the project began with the expectation that subagents might execute tasks in parallel and later attempted to implement four packs concurrently, whereas the observed outcome in both cases favoured one Muse Code session per feature worktree with tasks completed sequentially and reviewed by a human at feature granularity, a pattern that the workflow now enforces by refusing to work a task that another session has claimed and by treating the feature rather than the task as the review unit. The second concerns model and effort selection, because interface work repeatedly required more iteration than engine work at the same nominal effort, because Wonder at low and medium effort proved more cost-effective than Spark at extra-high effort for a class of interface fixes once its availability through the API was recognised, and because the open question recorded in `docs/pm-and-simple-game-engine.md`, namely whether feature and task development should be driven by Spark or by Wonder and at what effort, remains the correct framing even though daily practice settled on Wonder between medium and extra-high for much of the later work.

The third finding concerns skills as a deliberate workflow step rather than as background capability. Graphical interface quality improved materially only after interface-design and usability foundations skills were sought out, evaluated, and written into the prompt for the replay redesign, with explicit requirements concerning viewport obstruction, timeline unity, inspector placement, state visibility, and screenshot-based critique before completion, and the quality framework similarly benefited from reading two game testing skills in full, adopting their checkable ideas, and recording reasoned rejections for the remainder. The retrospective suggestion that finding and applying skills should be a named step in the workflow, supported by a find-skills capability, follows directly from those episodes, because in each case the limiting factor was not the model's ability to write code against a specification but the absence of a domain specification for what a usable operator interface or a sufficient test matrix should contain. A related observation is that prompt authorship for image generation benefited from the same delegation, because Muse Image 1.0 responded better to prompts composed by a language model from a brief and a checklist than to prompts typed directly, even though budget discipline during tool construction meant that possibility was explored less thoroughly than its later results suggested it deserved.

The fourth finding concerns the value of writing the contract down in a form the agent is required to load. The agent workflow file, the feature template, the candidate mechanic schema, the grounding document, and the pack folder convention all serve the same function in different domains, which is to convert a lesson learned through a failure, such as board state being hand-edited, a session being lost with its worktree, a term being used without definition, art being judged at the wrong scale, or a loader accumulating a hardcoded asset list, into a precondition that the next session encounters before it can repeat the failure. The project skill that triggers on natural requests to work on, review, or merge a feature and immediately loads the canonical workflow is the most developed instance of that pattern, because it allows the human to speak in terms of features while ensuring that claim checks, worktree handling, evidence capture, screenshot and session preservation, verifier execution for sanity-check features, and merge verification are performed in the same order on every occasion. The cost of that rigour is visible in the size of the resulting system, which at the time of writing comprises eighty-six board features including eighty-four exported specifications, thirty Python test modules under `tools/` that together run two hundred and seventy tests, a tools server of roughly fifteen hundred lines that hosts the asset tool, the project manager, the level preview, the game, and the worktree manager behind one process, and more than one hundred commits in which the per-task history remains legible, and that cost should be read as the price of making agent output reviewable rather than as incidental complexity.

## What remains uncertain

The infrastructure described in this report reduces several uncertainties without yet resolving the central one with which the project began. It is now possible to state with evidence whether a mechanic implements its specified rules, whether its teaching room can be won only by playing it, whether recorded proof replays deterministically, whether generated art matches the shipped sprites at the size the player will see, and what any of that work cost against a fixed budget with an automatic stop. It is not yet possible on the present evidence to state whether an agent can sequence those verified mechanics into levels whose pacing sustains interest across a full game, because synergy rooms were explicitly deferred within the sanity-check programme, the level roadmap contains only a small number of candidates that required human correction and combination, and no composed level set has yet been subjected to the same session-based scrutiny that individual mechanics now receive. The honest status of the central question is therefore that the measurement apparatus for answering it has been built and exercised on units, while the experiment that would answer it at level scale remains to be run.

Other open questions are narrower but may determine whether that experiment is run in the present engine at all. Stylistic consistency across generated tiles remains unresolved, with the reference-screenshot extraction idea and a possible unified tileset both deferred pending budget and an engine decision, and graphical interface assets that require precise slicing still depend on manual finishing outside the generation loop. The project manager may be more elaborate than the single-threaded workflow it ultimately served requires, and the notes on the engine refactor raise the alternative of porting the game to a different engine, or to three dimensions, in pursuit of a stronger visual outcome, while recording the decision to remain with the practical two-dimensional implementation for the present. Character animation for Jolly, evidenced by the pose, profile, and walk-cycle material under `screenshots/`, likewise remains exploratory rather than integrated as a finished locomotion system. Each of those questions is now at least posed against a codebase in which a proposed answer can be implemented as a feature, played in a test room, recorded, replayed, costed, and reviewed, which is the condition the hackathon set out to create.
